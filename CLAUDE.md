# AI-асистент чергового інженера

Семестровий проєкт з дисципліни «Технології штучного інтелекту»: інтелектуальна
мультимодальна система моніторингу Windows-серверів. Система збирає метрики,
виявляє аномалії, прогнозує заповнення дисків, формує алерти з поясненням і
відповідає на питання за базою знань (ранбуками) через Telegram-бота та
веб-додаток (Streamlit: дашборд + чат).

Технічне завдання лежить у `docs/tz.pdf` (лише локально, у Git не
публікується — див. `.gitignore`). Термін — приблизно 2 тижні.

## Статус цього файлу

Структура, схема БД і план нижче — стартова версія, а не догма. Якщо
потрібно щось змінити, спершу поясни навіщо і дочекайся згоди. Після зміни
онови відповідний розділ цього файлу, щоб він завжди відповідав реальному
стану проєкту. Поки дані симульовані, при зміні схеми БД базу можна
видалити й перегенерувати симулятором.

## Середовище

- Windows, PowerShell, Python 3.13 у віртуальному середовищі `.venv`
  (`py -V:3.13 -m venv .venv`).
- На машині також встановлено Python 3.15, тому завжди працюй через `.venv`
  (створений з 3.13), а не через системний `python`.
- Ключі API лише у `.env` (шаблон — `.env.example`); `.env` у `.gitignore`.
  Ніколи не вписуй ключі в код; модулі читають їх лише через
  `core/config.py` (`get_setting()`). Перевірка: `python -m core.config`.
  Змінні в `.env`:
  `ANTHROPIC_API_KEY`, `GROQ_API_KEY`, `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_ALLOWED_IDS` (через кому), `LLM_PROVIDER` (claude або groq),
  `INGEST_API_KEY` (ключ агента для REST API), `DASHBOARD_PASSWORD`
  (пароль входу в дашборд).
- Репозиторій публічний: жодних реальних імен компаній, серверів чи
  внутрішніх адрес у коді, даних і документації.

## Архітектура

```
Джерела:    симулятор | агент → REST API (POST /ingest) | імпорт CSV / Excel
               ↓ (сирі дані в однаковому форматі)
Сховище:    SQLite | ChromaDB (ранбуки) | rules.yaml | ontology.yaml
               ↓
Підготовка: ETL: перевірка, пропуски, викиди, 1-хв сітка → metrics_clean
               ↓
Обробка:    аналізатор, кожні 5 хв: аномалії, прогноз, правила → алерти
               ↓
Інтелект:   асистент: намір і емоція → свіжі факти → RAG → LLM → відповідь
               ↕
Інтерфейси: Telegram-бот | Streamlit (дашборд + чат) | REST API (GET /status, /alerts)
```

Принципи:

- Формат сирих даних визначає те, що реально збирає агент (psutil);
  симулятор імітує саме цей формат. Решта системи не розрізняє реальні
  та симульовані дані (симульовані сервери мають імена `sim-*`).
- Сирі дані не змінюються. Аналізатор і дашборд читають очищені дані
  з `metrics_clean`, які готує ETL (`core/etl.py`).
- Викиди. Неможливі значення (CPU > 100 %, від'ємний диск) ETL відкидає
  завжди. Статистичні викиди лишаються в `metrics_clean` з позначкою
  `is_outlier`: детектор аномалій їх бачить, а при навчанні прогнозу
  і регресії вони прибираються.
- Увесь час у базі зберігається в UTC.
- LLM нічого не рахує і не вигадує чисел. Числа рахує код, а LLM лише
  формулює відповідь з блоків ФАКТИ / ВИСНОВКИ ПРАВИЛ / РАНБУКИ.
  Якщо LLM недоступна — відповідь збирається за шаблоном.
- Кожен зовнішній сервіс живе в одному модулі (`llm.py`, `stt.py`, `tts.py`,
  `vision.py`, `emotion.py`), щоб його можна було замінити.
- Агент пише дані лише через REST API з ключем `INGEST_API_KEY`.
  Симулятор пише в БД напряму.
- Дашборд відкривається лише після введення пароля `DASHBOARD_PASSWORD`.
- Бот нічого не виконує на серверах, лише радить.
- Бот відповідає лише користувачам зі списку `TELEGRAM_ALLOWED_IDS`.
  Іншим — коротка відмова без виклику LLM (кожен виклик витрачає кредити).
- Якщо черговий у стресі, бот відповідає коротше, покроково
  і пропонує ескалацію.

## Схема БД (SQLite)

Сирі дані (пишуть агент, симулятор, імпорт CSV):

- `servers` — id, name, kind (real/sim), description
- `metrics` — ts, server_id, cpu_pct, ram_pct, disk_read_mbs, disk_write_mbs,
  net_in_mbs, net_out_mbs, app_response_ms, app_error_pct, source
- `disk_usage` — ts, server_id, drive, used_pct, free_gb, total_gb
- `process_snapshots` — ts, server_id, name, pid, cpu_pct, ram_mb, app_pool
- `folder_sizes` — ts, server_id, path, size_gb
- `service_status` — ts, server_id, name, kind (service/apppool), status
- `events` — ts, server_id, log, source, event_id, level, message
- `checks` — ts, server_id, check_type (http/cert/backup/sql_port), ok, value, details
- `sim_incidents` — id, server_id, scenario, started_at, ended_at
  (пише симулятор; це «правильні відповіді» для оцінки F1 детектора аномалій
  і класифікатора)

Оброблені дані (пишуть ETL і аналізатор):

- `metrics_clean` — ts (1-хв сітка, UTC), server_id, metric
  (наприклад `cpu_pct`, `disk_used_pct:C:`), value, is_imputed, is_outlier.
  Пише ETL. Одна метрика — один рядок, тому нова метрика від агента
  не змінює схему
- `anomalies` — ts, server_id, metric, score, is_anomaly, model
- `predictions` — ts, server_id, metric, model, horizon_h, predicted_value,
  hours_to_threshold
- `alerts` — id, server_id, rule_id, severity, status (open/acked/resolved),
  opened_at, updated_at, notified_at, acked_at, resolved_at, facts_json,
  justification, message (політика алертів — у `docs/milestones.md`)

Користувачі та діалоги (пишуть бот і веб-чат):

- `users` — id, telegram_id, name, notify
- `messages` — id, user_id, channel (telegram/web), ts, role, content,
  intent, emotion, input_type (text/voice/image/csv/xlsx/video), latency_ms,
  llm_provider, tokens_in, tokens_out
- `uploads` — id, user_id, ts, type, filename, status, result_summary

Якість моделей (пишуть скрипти оцінки):

- `model_metrics` — ts, model, dataset, metric, value

## Вісім типових інцидентів

Пороги взято з шаблону Zabbix «Windows by Zabbix agent» і з колекції
awesome-prometheus-alerts.

| Правило | Умова | Критичність |
|---|---|---|
| Диск заповнюється | зайнято > 80 % (увага), > 90 % (критично) або до 95 % лишилося < 72 год (увага) / < 24 год (критично) | увага / критично |
| Високе CPU | > 90 % протягом 5 хв | увага |
| Мало пам'яті / витік | > 90 % протягом 5 хв або подія Resource-Exhaustion-Detector 2004 | увага / критично |
| Служба зупинилась | служба зі списку не працює або події 7031 / 7034 | критично |
| Пул IIS впав | події WAS 5002 / 5009 / 5010 / 5011 або пул зупинено | критично |
| Сайт не відповідає | HTTP-код ≠ 200 або відповідь > 2 с | критично |
| Сертифікат закінчується | < 30 днів (увага), < 7 днів (критично) | увага / критично |
| Немає свіжого бекапу | останній `.bak` старший за 24 год | увага |

Для кожного правила є ранбук у `knowledge/runbooks/`.

## Вимоги ТЗ, які треба закрити

- Telegram-бот (асинхронний): діалог з LLM на базі знань, прийом і валідація
  даних (текст, CSV, Excel, зображення, аудіо; відео — необов'язково),
  сповіщення і звіти, посилання на дашборд.
- Клієнтський веб-додаток із чатом.
- Дашборд (вхід за паролем): KPI, динаміка, прогнози, кореляційна матриця.
- ML: очищення, викиди, нормалізація, ETL; регресія, часові ряди,
  класифікація, кластеризація, виявлення аномалій. DL — готові моделі.
- База знань: векторна БД + онтологія + правила з обґрунтуванням висновків.
- БД зі схемою та ER-діаграмою. Зберігає профілі користувачів, логи діалогів,
  сирі й оброблені дані, метрики моделей.
- REST API для взаємодії модулів (етап «Модульна інтеграція» ТЗ).
- Голос: STT і TTS. Емоції (Emotion AI): з голосу і тексту.
  Комп'ютерний зір: аналіз скріншотів.
- Метрики: Accuracy/F1, MSE/MAE/R², RAGAS, стійкість бота
  (цілі: `/status` до 1 с, текст з LLM до 5 с, голос до 10 с — 95-й перцентиль).
- GitHub, requirements.txt, Dockerfile / docker-compose.yml, README.md.
- Пояснювальна записка 25–40 сторінок за ДСТУ: обґрунтування стеку, схема
  архітектури з клієнтською і серверною частинами, математичний опис
  алгоритмів і моделей з метриками якості, інструкція розгортання,
  посібник користувача.

## Цільові команди запуску

```powershell
.venv\Scripts\Activate.ps1
python -m simulator.simulator                # симулятор
python -m uvicorn api.app:app --port 8000    # REST API
python -m agent.agent                        # агент (від імені адміністратора)
python -m core.analyzer                      # аналізатор
python -m bot.bot                            # Telegram-бот
streamlit run web/app.py                     # веб-додаток
```
