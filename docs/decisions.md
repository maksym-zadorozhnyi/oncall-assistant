# Базовий стек (обрано до початку розробки)

## LLM
- **Обрали:** Claude API (`claude-haiku-5-5` — маршрутизація і більшість
  відповідей, `claude-sonnet-5-5` — складні відповіді і RAGAS).
- **Альтернативи:** Groq — безкоштовний і швидкий, але на безкоштовному тарифі
  8 тис. токенів за хвилину (лишаємо для Whisper і для порівняння); Gemini —
  безкоштовний тариф використовує дані для покращення продуктів Google;
  Ollama — потрібен потужний ПК, малі моделі слабші в українській.
- **Чому:** краща українська, читає зображення, оплачується щомісячними
  API-кредитами підписки Max.

## Основна БД
- **Обрали:** SQLite (`data/oncall.db`).
- **Альтернативи:** PostgreSQL.
- **Чому:** не потрібен окремий сервер, достатньо для демо, ТЗ прямо дозволяє.

## Векторна БД
- **Обрали:** ChromaDB.
- **Альтернативи:** FAISS, Qdrant.
- **Чому:** проста, локальна, зберігає метадані фрагментів (назва ранбука,
  розділ) поряд з векторами.

## Telegram-бот
- **Обрали:** aiogram 3.
- **Альтернативи:** python-telegram-bot.
- **Чому:** асинхронний з коробки; ТЗ називає його першим.

## Веб-додаток і дашборд
- **Обрали:** Streamlit + Plotly.
- **Альтернативи:** Gradio, Dash, Grafana.
- **Чому:** дашборд і чат в одному застосунку, лише Python.

## Агент збору даних
- **Обрали:** власний скрипт на psutil + PowerShell.
- **Альтернативи:** windows_exporter, Telegraf, Zabbix agent — потребують
  окремої системи зберігання.
- **Чому:** одна мова з рештою проєкту, дані одразу в нашому форматі,
  легко додати власні перевірки (сертифікати, бекапи, пули IIS).

## Пороги правил
- **Обрали:** пороги з офіційного шаблону Zabbix «Windows by Zabbix agent»
  і колекції awesome-prometheus-alerts.
- **Альтернативи:** власні пороги «на око».
- **Чому:** перевірені практикою значення, на які можна послатися в записці.

# Рішення після звірки з ТЗ (2026-11-17)

## Предметна галузь
- **Обрали:** адаптацію напряму №2 ТЗ (стан обладнання + оператор):
  обладнання — Windows-сервери, оператор — черговий інженер.
- **Альтернативи:** напрями №1 (медицина) і №3 (агро).
- **Чому:** реальна експертиза автора (DevOps, Windows Server, IIS);
  можна зібрати власні реальні дані агентом.
- **Статус:** чекає підтвердження викладача.

## Emotion AI
- **Обрали:** емоція чергового з голосових (готова SER-модель з Hugging Face)
  і з тексту (Claude, у тому ж виклику, що й намір). Поле `messages.emotion`.
- **Альтернативи:** емоції з обличчя (MediaPipe + CNN); власна SER-модель на MFCC.
- **Чому:** голос і текст уже йдуть через бота, камера не потрібна;
  емоція з тексту не потребує окремого виклику LLM.
- **Ризик:** відкриті SER-датасети і моделі переважно англомовні —
  точність на українському мовленні може бути нижчою, ніж на тестовому наборі.

## Комп'ютерний нюх, жести, відео
- **Обрали:** нюх і жести поки не робимо; відео — необов'язковий крок 5.5.
- **Альтернативи для нюху:** «датчики повітря серверної» (Smoke Detection
  + симулятор, PCA + Random Forest); подати класифікатор інцидентів як «нюх».
- **Чому:** обмежений термін; подавати класифікатор інцидентів як «нюх»
  було б натяжкою. Нюх — лише якщо цього вимагатиме викладач.

## Обробка викидів
- **Обрали:** неможливі значення відкидаються завжди; статистичні викиди
  позначаються `is_outlier`, прибираються з навчання прогнозу і регресії,
  але лишаються для детектора аномалій.
- **Альтернативи:** видаляти всі викиди (буквально за ТЗ); не чіпати взагалі.
- **Чому:** в моніторингу викид часто і є інцидентом — видалення осліпило б
  детектор; водночас одиничний сплеск спотворює лінійний прогноз диска.

## REST API
- **Обрали:** FastAPI + uvicorn: `POST /ingest` (ключ `X-API-Key`),
  `GET /status`, `GET /alerts`.
- **Альтернативи:** Flask; без API (усі модулі пишуть у спільну SQLite).
- **Чому:** етап «Модульна інтеграція» ТЗ; агент на іншій машині не повинен
  мати прямий доступ до БД; FastAPI асинхронний, перевіряє вхідні дані
  і сам будує документацію `/docs`.

## Прийом даних
- **Обрали:** CSV і Excel (.xlsx, через вже наявний openpyxl) з валідацією
  типу, розміру і колонок; відео — необов'язково, кадри через OpenCV.
- **Альтернативи:** лише CSV.
- **Чому:** ТЗ прямо називає CSV/Excel; Excel — звичний формат вивантажень
  у Windows-середовищі.

## Захист дашборду
- **Обрали:** пароль з `.env` (`DASHBOARD_PASSWORD`); необов'язково —
  посилання з бота з одноразовим токеном.
- **Альтернативи:** streamlit-authenticator; OAuth; без захисту.
- **Чому:** ТЗ згадує «авторизований кабінет»; пароль не потребує
  нових бібліотек і достатній для демо.

## Цілі швидкодії
- **Обрали:** 95-й перцентиль: `/status` до 1 с, текст з LLM до 5 с, голос до 10 с.
- **Чому:** ТЗ вимагає низьку затримку; `/status` не викликає LLM,
  текст — один-два виклики LLM, голос — ще STT і TTS.

## Глибоке навчання
- **Обрали:** DL покривають готові моделі (Claude, Whisper, ембединги,
  SER-модель); опційно — автоенкодер на PyTorch для аномалій у фазі 6.
- **Альтернативи:** власні LSTM/CNN для прогнозу чи аномалій.
- **Чому:** термін ~2 тижні; готові моделі якісніші; автоенкодер дасть
  порівняння з Isolation Forest, якщо лишиться час.

## Допоміжні бібліотеки: python-dotenv і PyYAML (2026-11-18)
- **Обрали:** `python-dotenv` — читання ключів з `.env`; `PyYAML` — читання
  `rules.yaml`, `ontology.yaml`, `config.yaml`.
- **Альтернативи:** змінні середовища Windows замість `.env`; JSON або TOML
  (`tomllib` вбудований у Python) замість YAML.
- **Чому:** `.env` — один файл для всіх модулів і Docker; YAML легко читати
  й правити вручну, коментарі дозволені (у JSON — ні).

## Залежності додаються поступово (2026-11-18)
- **Обрали:** у `requirements.txt` лише бібліотеки поточної фази, точні версії (`==`).
- **Альтернативи:** повний список одразу; повний `pip freeze`.
- **Чому:** sentence-transformers тягне PyTorch (кілька ГБ) — ставимо, коли
  знадобиться; точні версії дають відтворюваність, а короткий список лишається
  читабельним.

## CPU процесу в шкалі 0–100 % (2026-11-18)
- **Обрали:** `process_snapshots.cpu_pct` = значення psutil ÷ кількість
  логічних ядер — як у диспетчері завдань Windows.
- **Альтернативи:** «сире» значення psutil (відносно одного ядра; на 16 ядрах
  процес може показати до 1600 %).
- **Чому:** CPU процесу і CPU сервера (`metrics.cpu_pct`) в одній шкалі —
  їх можна порівнювати («процес займає 40 % з 45 % загального навантаження»);
  звично для адміністратора Windows.

## Швидкості дисків і мережі — різниця двох замірів (2026-11-18)
- **Обрали:** агент робить два заміри лічильників з паузою 2 с і ділить
  різницю на фактичний час між замірами; мережа — сума всіх адаптерів
  без loopback, у МБ/с (мегабайти, не мегабіти).
- **Альтернативи:** `cpu_percent(interval=2)` — блокує виклик окремо для
  кожного показника; лічильники Windows (PowerShell `Get-Counter`).
- **Чому:** перший виклик `cpu_percent()` у psutil завжди повертає 0, тож
  без двох замірів не обійтися; одна спільна пауза для CPU, процесів, дисків
  і мережі — усі показники за той самий проміжок часу.

## Симулятор: місцевий час — фіксований UTC+2 (2026-11-18)
- **Обрали:** добовий і тижневий цикли рахуються за місцевим часом
  UTC+2 без переходу на літній час; у базу пишеться UTC.
- **Альтернативи:** `zoneinfo("Europe/Kyiv")` з урахуванням літнього часу.
- **Чому:** на Windows для `zoneinfo` потрібна додаткова бібліотека `tzdata`;
  для симуляції година зсуву влітку неважлива.

## Симулятор: будова (2026-11-18)
- **Обрали:** профілі серверів у `simulator/profiles.yaml`; сценарій — функція,
  що змінює стан сервера залежно від хвилин від початку інциденту, спільна
  для історії, живого потоку і ручного запуску; живий режим вмикає сценарій
  рядком у `sim_incidents` з `ended_at = NULL`; на сервері — один сценарій
  одночасно.
- **Альтернативи:** окрема логіка для історії і для демо; сценарій як
  окремий процес; прапорець у файлі.
- **Чому:** інциденти в історії (на чому вчиться ML) такі самі, як на демо;
  сценарій можна ввімкнути з іншого вікна, а згодом — з бота чи вебсторінки;
  один сценарій на сервер дає однозначні мітки для оцінки моделей.

## Симулятор: ланцюжки інцидентів і догенерація (2026-11-18)
- **Обрали:** в історії 2–3 ланцюжки, що накладаються (`memory_leak` →
  `apppool_crash`, `disk_fill` → `backup_stale`), відповідно до зв'язку
  `can_cause` в онтології; у живому режимі — один сценарій на сервер.
  Живий режим після паузи догенеровує пропущені хвилини sim-* лише нормальною
  поведінкою; реальні сервери ніколи не догенеровуються.
- **Альтернативи:** лише ізольовані інциденти; залишати розриви в даних sim-*.
- **Чому:** у реальності інциденти тягнуть один одного — моделі й асистент
  мають бачити такі випадки, а онтологія пояснює зв'язок. Дірка в даних
  після вимкненого ноутбука — артефакт демо, а не подія на сервері.

## ML: моделі не прив'язуються до конкретних серверів (2026-11-18)
- **Обрали:** окрема модель аномалій на сервер; відносні ознаки (відхилення
  від норми сервера в цю годину); розігрів 24 год — лише правила;
  перенавчання щоночі; класифікатор з порогом впевненості («тип не
  визначено»); перевірка узагальнення sim-1 → sim-2 і на my-pc.
- **Альтернативи:** одна спільна модель на абсолютних значеннях.
- **Чому:** «норма» вебсервера і сервера БД різна (RAM 60 % і 80 % — обидві
  норма); спільна модель на абсолютних значеннях вивчила б sim-1 і sim-2,
  а не поняття «аномалія», і не працювала б на новому сервері.

## Частота збору — однакова для агента і симулятора (2026-11-18)
- **Обрали:** щохвилини — метрики, диски, HTTP, порт SQL; раз на 5 хв —
  процеси, служби (і одразу при зміні стану), розміри тек; щогодини —
  сертифікат і бекап; події — коли стаються. Без окремих режимів.
- **Альтернативи:** теки щогодини (дешевше); частіші заміри лише в живому режимі.
- **Чому:** при щогодинних замірах тек 10-хвилинний `disk_fill` на демо
  міг би не потрапити в жоден знімок; один розклад для всіх — простіше
  і чесніше (історія виглядає так само, як живі дані).

## Процеси: топ-5 за CPU + топ-5 за RAM (2026-11-18)
- **Обрали:** у кожному знімку — топ-5 за CPU і топ-5 за RAM без повторів.
- **Альтернативи:** лише топ-5 за CPU; окремий список процесів, за якими стежимо.
- **Чому:** процес з витоком пам'яті може мати мало CPU і не потрапити в
  топ за CPU; окремий список ускладнив би агент без потреби.

## Інвентар сервера (2026-11-18)
- **Обрали:** колонка `servers.inventory_json` (+ час оновлення): сайт → пул
  (`appcmd list app`) і служба → exe (`Win32_Service`); лише поточний стан.
- **Альтернативи:** окрема таблиця з історією змін; брати зв'язки з
  `profiles.yaml` (справжній агент такого файлу не має).
- **Чому:** без цього бот не скаже, який сайт ляже при падінні пулу і який
  процес належить службі; історія змін для наших питань не потрібна.

## Симулятор: значення checks.ok (2026-11-18)
- **Обрали:** `ok` — результат самої перевірки: HTTP — код 200 і відповідь
  до таймауту 2 с; сертифікат — дійсний; бекап — останнє завдання бекапу
  успішне; порт SQL — відкритий. Пороги «скільки днів / годин — це погано»
  живуть у правилах (`rules.yaml`), не в агенті.
- **Чому:** агент лише вимірює, а висновки робить база знань — так їх можна
  пояснити і змінити в одному місці.

## Кінці рядків — .gitattributes (2026-11-18)
- **Обрали:** у репозиторії текстові файли з LF, скрипти Windows (.ps1, .bat,
  .cmd) — з CRLF, картинки / PDF / БД — двійкові.
- **Альтернативи:** покладатися на `core.autocrlf` кожної машини.
- **Чому:** однаковий результат на будь-якому ПК; LF потрібен для Docker
  (скрипти з CRLF у Linux-контейнері не запускаються).

## «Ключ відповідей» окремо від даних (2026-11-18)
- **Обрали:** параметри інциденту (служба, пул, тека) зберігаються лише
  в `sim_incidents.params_json`; аналізатор, бот і ML його не читають.
- **Альтернативи:** зберігати параметри в звичайних таблицях даних.
- **Чому:** інакше моделі й бот могли б «підглянути» відповідь, і оцінка
  якості була б завищеною; `--details` показує поруч ключ і те, що видно
  з даних, — так перевіряємо, що причину можна знайти чесно.

## Онтологія на кроці 1.2
- **Обрали:** чернетку `knowledge/ontology.yaml` робимо разом з ER-діаграмою.
- **Чому:** ТЗ ставить онтологію на аналітичний етап поряд з ER-діаграмою;
  у кроці 3.2 лише доповнюємо посиланнями на ранбуки.

## Симулятор заморожено, живий потік — перед алертами (2026-11-18)
- **Обрали:** закрити крок 1.5 як є; міняти симулятор лише тоді, коли тест
  показав, що бот помиляється через дані. Кроки 1.6–1.7 (живий потік
  і сценарії) робимо одним кроком після 2.3, перед 2.4.
- **Альтернативи:** далі шліфувати тексти подій; робити живий потік
