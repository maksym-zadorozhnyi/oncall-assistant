# Базовий стек (обрано до початку розробки)

## LLM
- **Обрали:** Claude API (`claude-haiku-5-5` — маршрутизація і більшість
  відповідей, `claude-sonnet-5-5` — складні відповіді і RAGAS).
- **Альтернативи:** Groq — безкоштовний і швидкий, але на безкоштовному тарифі
  8 тис. токенів за хвилину (лишаємо для Whisper і для порівняння); Gemini —
  безкоштовний тариф використовує дані для покращення продуктів Google;
  Ollama — потрібен потужний ПК, малі моделі слабші в українській.
- **Чому:** краща українська, читає зображення, оплачується щомісячними
  API-кредитами підписки Max.

## Основна БД
- **Обрали:** SQLite (`data/oncall.db`).
- **Альтернативи:** PostgreSQL.
- **Чому:** не потрібен окремий сервер, достатньо для демо, ТЗ прямо дозволяє.

## Векторна БД
- **Обрали:** ChromaDB.
- **Альтернативи:** FAISS, Qdrant.
- **Чому:** проста, локальна, зберігає метадані фрагментів (назва ранбука,
  розділ) поряд з векторами.

## Telegram-бот
- **Обрали:** aiogram 3.
- **Альтернативи:** python-telegram-bot.
- **Чому:** асинхронний з коробки; ТЗ називає його першим.

## Веб-додаток і дашборд
- **Обрали:** Streamlit + Plotly.
- **Альтернативи:** Gradio, Dash, Grafana.
- **Чому:** дашборд і чат в одному застосунку, лише Python.

## Агент збору даних
- **Обрали:** власний скрипт на psutil + PowerShell.
- **Альтернативи:** windows_exporter, Telegraf, Zabbix agent — потребують
  окремої системи зберігання.
- **Чому:** одна мова з рештою проєкту, дані одразу в нашому форматі,
  легко додати власні перевірки (сертифікати, бекапи, пули IIS).

## Пороги правил
- **Обрали:** пороги з офіційного шаблону Zabbix «Windows by Zabbix agent»
  і колекції awesome-prometheus-alerts.
- **Альтернативи:** власні пороги «на око».
- **Чому:** перевірені практикою значення, на які можна послатися в записці.

# Рішення після звірки з ТЗ (2026-11-17)

## Предметна галузь
- **Обрали:** адаптацію напряму №2 ТЗ (стан обладнання + оператор):
  обладнання — Windows-сервери, оператор — черговий інженер.
- **Альтернативи:** напрями №1 (медицина) і №3 (агро).
- **Чому:** реальна експертиза автора (DevOps, Windows Server, IIS);
  можна зібрати власні реальні дані агентом.
- **Статус:** чекає підтвердження викладача.

## Emotion AI
- **Обрали:** емоція чергового з голосових (готова SER-модель з Hugging Face)
  і з тексту (Claude, у тому ж виклику, що й намір). Поле `messages.emotion`.
- **Альтернативи:** емоції з обличчя (MediaPipe + CNN); власна SER-модель на MFCC.
- **Чому:** голос і текст уже йдуть через бота, камера не потрібна;
  емоція з тексту не потребує окремого виклику LLM.
- **Ризик:** відкриті SER-датасети і моделі переважно англомовні —
  точність на українському мовленні може бути нижчою, ніж на тестовому наборі.

## Комп'ютерний нюх, жести, відео
- **Обрали:** нюх і жести поки не робимо; відео — необов'язковий крок 5.5.
- **Альтернативи для нюху:** «датчики повітря серверної» (Smoke Detection
  + симулятор, PCA + Random Forest); подати класифікатор інцидентів як «нюх».
- **Чому:** обмежений термін; подавати класифікатор інцидентів як «нюх»
  було б натяжкою. Нюх — лише якщо цього вимагатиме викладач.

## Обробка викидів
- **Обрали:** неможливі значення відкидаються завжди; статистичні викиди
  позначаються `is_outlier`, прибираються з навчання прогнозу і регресії,
  але лишаються для детектора аномалій.
- **Альтернативи:** видаляти всі викиди (буквально за ТЗ); не чіпати взагалі.
- **Чому:** в моніторингу викид часто і є інцидентом — видалення осліпило б
  детектор; водночас одиничний сплеск спотворює лінійний прогноз диска.

## REST API
- **Обрали:** FastAPI + uvicorn: `POST /ingest` (ключ `X-API-Key`),
  `GET /status`, `GET /alerts`.
- **Альтернативи:** Flask; без API (усі модулі пишуть у спільну SQLite).
- **Чому:** етап «Модульна інтеграція» ТЗ; агент на іншій машині не повинен
  мати прямий доступ до БД; FastAPI асинхронний, перевіряє вхідні дані
  і сам будує документацію `/docs`.

## Прийом даних
- **Обрали:** CSV і Excel (.xlsx, через вже наявний openpyxl) з валідацією
  типу, розміру і колонок; відео — необов'язково, кадри через OpenCV.
- **Альтернативи:** лише CSV.
- **Чому:** ТЗ прямо називає CSV/Excel; Excel — звичний формат вивантажень
  у Windows-середовищі.

## Захист дашборду
- **Обрали:** пароль з `.env` (`DASHBOARD_PASSWORD`); необов'язково —
  посилання з бота з одноразовим токеном.
- **Альтернативи:** streamlit-authenticator; OAuth; без захисту.
- **Чому:** ТЗ згадує «авторизований кабінет»; пароль не потребує
  нових бібліотек і достатній для демо.

## Цілі швидкодії
- **Обрали:** 95-й перцентиль: `/status` до 1 с, текст з LLM до 5 с, голос до 10 с.
- **Чому:** ТЗ вимагає низьку затримку; `/status` не викликає LLM,
  текст — один-два виклики LLM, голос — ще STT і TTS.

## Глибоке навчання
- **Обрали:** DL покривають готові моделі (Claude, Whisper, ембединги,
  SER-модель); опційно — автоенкодер на PyTorch для аномалій у фазі 6.
- **Альтернативи:** власні LSTM/CNN для прогнозу чи аномалій.
- **Чому:** термін ~2 тижні; готові моделі якісніші; автоенкодер дасть
  порівняння з Isolation Forest, якщо лишиться час.

## Допоміжні бібліотеки: python-dotenv і PyYAML (2026-11-18)
- **Обрали:** `python-dotenv` — читання ключів з `.env`; `PyYAML` — читання
  `rules.yaml`, `ontology.yaml`, `config.yaml`.
- **Альтернативи:** змінні середовища Windows замість `.env`; JSON або TOML
  (`tomllib` вбудований у Python) замість YAML.
- **Чому:** `.env` — один файл для всіх модулів і Docker; YAML легко читати
  й правити вручну, коментарі дозволені (у JSON — ні).

## Залежності додаються поступово (2026-11-18)
- **Обрали:** у `requirements.txt` лише бібліотеки поточної фази, точні версії (`==`).
- **Альтернативи:** повний список одразу; повний `pip freeze`.
- **Чому:** sentence-transformers тягне PyTorch (кілька ГБ) — ставимо, коли
  знадобиться; точні версії дають відтворюваність, а короткий список лишається
  читабельним.

## CPU процесу в шкалі 0–100 % (2026-11-18)
- **Обрали:** `process_snapshots.cpu_pct` = значення psutil ÷ кількість
  логічних ядер — як у диспетчері завдань Windows.
- **Альтернативи:** «сире» значення psutil (відносно одного ядра; на 16 ядрах
  процес може показати до 1600 %).
- **Чому:** CPU процесу і CPU сервера (`metrics.cpu_pct`) в одній шкалі —
  їх можна порівнювати («процес займає 40 % з 45 % загального навантаження»);
  звично для адміністратора Windows.

## Швидкості дисків і мережі — різниця двох замірів (2026-11-18)
- **Обрали:** агент робить два заміри лічильників з паузою 2 с і ділить
  різницю на фактичний час між замірами; мережа — сума всіх адаптерів
  без loopback, у МБ/с (мегабайти, не мегабіти).
- **Альтернативи:** `cpu_percent(interval=2)` — блокує виклик окремо для
  кожного показника; лічильники Windows (PowerShell `Get-Counter`).
- **Чому:** перший виклик `cpu_percent()` у psutil завжди повертає 0, тож
  без двох замірів не обійтися; одна спільна пауза для CPU, процесів, дисків
  і мережі — усі показники за той самий проміжок часу.

## Симулятор: місцевий час — фіксований UTC+2 (2026-11-18)
- **Обрали:** добовий і тижневий цикли рахуються за місцевим часом
  UTC+2 без переходу на літній час; у базу пишеться UTC.
- **Альтернативи:** `zoneinfo("Europe/Kyiv")` з урахуванням літнього часу.
- **Чому:** на Windows для `zoneinfo` потрібна додаткова бібліотека `tzdata`;
  для симуляції година зсуву влітку неважлива.

## Симулятор: будова (2026-11-18)
- **Обрали:** профілі серверів у `simulator/profiles.yaml`; сценарій — функція,
  що змінює стан сервера залежно від хвилин від початку інциденту, спільна
  для історії, живого потоку і ручного запуску; живий режим вмикає сценарій
  рядком у `sim_incidents` з `ended_at = NULL`; на сервері — один сценарій
  одночасно.
- **Альтернативи:** окрема логіка для історії і для демо; сценарій як
  окремий процес; прапорець у файлі.
- **Чому:** інциденти в історії (на чому вчиться ML) такі самі, як на демо;
  сценарій можна ввімкнути з іншого вікна, а згодом — з бота чи вебсторінки;
  один сценарій на сервер дає однозначні мітки для оцінки моделей.

## Симулятор: ланцюжки інцидентів і догенерація (2026-11-18)
- **Обрали:** в історії 2–3 ланцюжки, що накладаються (`memory_leak` →
  `apppool_crash`, `disk_fill` → `backup_stale`), відповідно до зв'язку
  `can_cause` в онтології; у живому режимі — один сценарій на сервер.
  Живий режим після паузи догенеровує пропущені хвилини sim-* лише нормальною
  поведінкою; реальні сервери ніколи не догенеровуються.
- **Альтернативи:** лише ізольовані інциденти; залишати розриви в даних sim-*.
- **Чому:** у реальності інциденти тягнуть один одного — моделі й асистент
  мають бачити такі випадки, а онтологія пояснює зв'язок. Дірка в даних
  після вимкненого ноутбука — артефакт демо, а не подія на сервері.

## ML: моделі не прив'язуються до конкретних серверів (2026-11-18)
- **Обрали:** окрема модель аномалій на сервер; відносні ознаки (відхилення
  від норми сервера в цю годину); розігрів 24 год — лише правила;
  перенавчання щоночі; класифікатор з порогом впевненості («тип не
  визначено»); перевірка узагальнення sim-1 → sim-2 і на my-pc.
- **Альтернативи:** одна спільна модель на абсолютних значеннях.
- **Чому:** «норма» вебсервера і сервера БД різна (RAM 60 % і 80 % — обидві
  норма); спільна модель на абсолютних значеннях вивчила б sim-1 і sim-2,
  а не поняття «аномалія», і не працювала б на новому сервері.

## Частота збору — однакова для агента і симулятора (2026-11-18)
- **Обрали:** щохвилини — метрики, диски, HTTP, порт SQL; раз на 5 хв —
  процеси, служби (і одразу при зміні стану), розміри тек; щогодини —
  сертифікат і бекап; події — коли стаються. Без окремих режимів.
- **Альтернативи:** теки щогодини (дешевше); частіші заміри лише в живому режимі.
- **Чому:** при щогодинних замірах тек 10-хвилинний `disk_fill` на демо
  міг би не потрапити в жоден знімок; один розклад для всіх — простіше
  і чесніше (історія виглядає так само, як живі дані).

## Процеси: топ-5 за CPU + топ-5 за RAM (2026-11-18)
- **Обрали:** у кожному знімку — топ-5 за CPU і топ-5 за RAM без повторів.
- **Альтернативи:** лише топ-5 за CPU; окремий список процесів, за якими стежимо.
- **Чому:** процес з витоком пам'яті може мати мало CPU і не потрапити в
  топ за CPU; окремий список ускладнив би агент без потреби.

## Інвентар сервера (2026-11-18)
- **Обрали:** колонка `servers.inventory_json` (+ час оновлення): сайт → пул
  (`appcmd list app`) і служба → exe (`Win32_Service`); лише поточний стан.
- **Альтернативи:** окрема таблиця з історією змін; брати зв'язки з
  `profiles.yaml` (справжній агент такого файлу не має).
- **Чому:** без цього бот не скаже, який сайт ляже при падінні пулу і який
  процес належить службі; історія змін для наших питань не потрібна.

## Симулятор: значення checks.ok (2026-11-18)
- **Обрали:** `ok` — результат самої перевірки: HTTP — код 200 і відповідь
  до таймауту 2 с; сертифікат — дійсний; бекап — останнє завдання бекапу
  успішне; порт SQL — відкритий. Пороги «скільки днів / годин — це погано»
  живуть у правилах (`rules.yaml`), не в агенті.
- **Чому:** агент лише вимірює, а висновки робить база знань — так їх можна
  пояснити і змінити в одному місці.

## Кінці рядків — .gitattributes (2026-11-18)
- **Обрали:** у репозиторії текстові файли з LF, скрипти Windows (.ps1, .bat,
  .cmd) — з CRLF, картинки / PDF / БД — двійкові.
- **Альтернативи:** покладатися на `core.autocrlf` кожної машини.
- **Чому:** однаковий результат на будь-якому ПК; LF потрібен для Docker
  (скрипти з CRLF у Linux-контейнері не запускаються).

## «Ключ відповідей» окремо від даних (2026-11-18)
- **Обрали:** параметри інциденту (служба, пул, тека) зберігаються лише
  в `sim_incidents.params_json`; аналізатор, бот і ML його не читають.
- **Альтернативи:** зберігати параметри в звичайних таблицях даних.
- **Чому:** інакше моделі й бот могли б «підглянути» відповідь, і оцінка
  якості була б завищеною; `--details` показує поруч ключ і те, що видно
  з даних, — так перевіряємо, що причину можна знайти чесно.

## Онтологія на кроці 1.2
- **Обрали:** чернетку `knowledge/ontology.yaml` робимо разом з ER-діаграмою.
- **Чому:** ТЗ ставить онтологію на аналітичний етап поряд з ER-діаграмою;
  у кроці 3.2 лише доповнюємо посиланнями на ранбуки.

## Симулятор заморожено, живий потік — перед алертами (2026-11-18)
- **Обрали:** закрити крок 1.5 як є; міняти симулятор лише тоді, коли тест
  показав, що бот помиляється через дані. Кроки 1.6–1.7 (живий потік
  і сценарії) робимо одним кроком після 2.3, перед 2.4.
- **Альтернативи:** далі шліфувати тексти подій; робити живий потік
  одразу після історії.
- **Чому:** реалізму історії вже досить для ETL, прогнозу і правил;
  дрібниці (Rapid-Fail, шістнадцятковий PID, LSN) не впливають на відповіді
  бота. Живі дані потрібні лише для алертів, тож ETL, прогноз і правила
  перевіряємо на історії, де інциденти вже відомі.

## Виняток із «симулятор заморожено»: повільне заповнення диска (2026-11-18)
- **Обрали:** параметр `cause` у `disk_fill` (новий тип інциденту не потрібен):
  `fast` — як було (години); `retention_stopped` — перестало працювати
  видалення старих файлів (sim-1 — щотижневе прибирання логів IIS, sim-2 —
  видалення старих бекапів на E:); `log_burst` — логи пишуться в 5–10 разів
  швидше кілька днів (sim-1 — логи IIS, sim-2 — `D:\SQLLogs`). В історії —
  по одному повільному випадку: sim-1 `retention_stopped` 12 днів (D: 37 →
  54 %, повільний тренд), sim-2 `retention_stopped` ~2,5 дня (E: сходинками
  67 → 96 %). `log_burst` — для живого режиму (крок 1.7). Кінець — «адміністратор
  помітив і почистив». За тиждень до повільного випадку на sim-2 збоїв бекапу
  не ставимо, інакше на E: на один бекап менше і сходинки йдуть нижче.
- **Альтернативи:** новий тип інциденту; лишити тільки швидке заповнення.
- **Чому:** найчастіший реальний випадок — повільне заповнення днями й
  тижнями; без нього прогнозу тренду (крок 2.2) нема на чому перевірятися.
  Дані — лише те, що бачить агент (ріст тек і диска, подія 2013 після 90 %);
  про те, що «зламалось прибирання», бот має здогадатися сам (немає щотижневого
  падіння, тека росте). На sim-2 довше 2,5 дня не можна: на 4-ту ніч бекап
  не поміститься і впаде сам — це був би збій без мітки в ключі відповідей.

## Тести: pytest (2026-11-18)
- **Обрали:** pytest; тести в `tests/`, запуск `python -m pytest`; кожен тест
  працює на тимчасовій базі, а не на `data/oncall.db`.
- **Альтернативи:** простий скрипт з `assert`; вбудований `unittest`.
- **Чому:** стандарт у Python, найкоротші тести, тимчасова тека з коробки
  (`tmp_path`); знадобиться в кожному наступному кроці.

## ETL: викид = короткий сплеск (2026-11-18)
- **Обрали:** значення — викид, якщо воно далеко і від рівня «до» (медіана
  30 хв перед ним), і від рівня «після» (медіана 30 хв після), з одного боку
  від обох. «Далеко» = більше за 3 звичайні розкиди (IQR; менший з вікон
  «до» і «після»), але не менше за мінімум показника (CPU 15 п. п., RAM
  10 п. п., помилки 5 п. п., для I/O і мережі — половина більшого з рівнів).
  Для дисків викидів не шукаємо. Секунди відкидаємо (а не округлюємо).
  Кожен запуск перераховує останню годину.
- **Альтернативи:** медіана лише за останню годину; z-оцінка за всю історію.
- **Чому:** медіана лише «до» позначала б сходинки (прибирання диска,
  бекап, перезапуск пулу) на ~30 хв, і прогноз диска викинув би саме дані
  після прибирання. Два виправлення знайдено на історії: розкид лише з вікна
  «до» роздувався наприкінці сплеску (cpu_spike 13 хв позначено на 8 хв
  з 13); відносний поріг від рівня «до» позначав коливання під час
  нічного бекапу (~200 хвилин I/O на sim-2). Обмеження: сплеск довший
  за ~15 хв — тимчасовий рівень, не викид; його бачить детектор аномалій.

## Поріг прогнозу диска — 90 % (2026-11-18)
- **Обрали:** прогноз рахує час до 90 % (параметр зі значенням за
  замовчуванням); смуги правила: < 72 год — увага, < 24 год — критично.
- **Альтернативи:** 95 % (як було в чернетці правила).
- **Чому:** 90 % — критичний поріг шаблону Zabbix і момент події 2013;
  швидкі `disk_fill` у симуляторі зупиняються на ~93 %, тож 95 %
  ніколи не досягається і точність прогнозу не перевірити.

## predictions: model — метод, kind — питання (2026-11-18)
- **Обрали:** `model` — назва методу (`linear`, `ets`, `chronos`…), нова
  колонка `kind` — тип питання (`trend` / `fast_growth` / `jump`); нові
  колонки `lower_value`, `upper_value` (інтервал) і `details_json`
  (швидкість, незвичний ріст, наступний стрибок). `metric` — як у
  `metrics_clean`: `disk_used_pct:<диск>`.
- **Альтернативи:** тип питання в `model`; окрема колонка на кожне поле.
- **Чому:** після зміни методу видно, хто зробив прогноз; правила 2.3
  шукають рядки за `kind`; окремих колонок було б 8–9, і більшість
  порожні в двох типах із трьох.

## Прогноз диска: лінійна регресія, усе «регулярне» — з даних (2026-11-18)
- **Обрали:** робочий метод — лінійна регресія (numpy, без нових бібліотек);
  наївний («як зараз», «як учора о цій порі») — лише для порівняння.
  Модуль бачить лише ряди `disk_used_pct:<диск>` і `disk_free_gb:<диск>`.
  Різкі підйоми й падіння шукаємо в 10-хв відрізках (≥ 0,5 п. п. за 10 хв,
  разом ≥ 3 п. п. не довше години). Регулярний стрибок — підйоми в той
  самий час доби (± 90 хв) і того самого розміру (± 30 % ГБ) у ≥ 3 різні
  дні з 7. «Зазвичай видаляють» — якщо після більшості таких стрибків було
  падіння того самого розміру; тоді свіжий стрибок не береться в тренд,
  поки не минув звичний час видалення. Пропущено видалення — стрибок
  потрапляє в тренд, і тренд ловить «сходи». Незвичний ріст — швидкість
  за 90 хв більша за 1 %/год і втричі більша за 90-й перцентиль швидкостей
  у ці ж хвилини доби за 7 днів (тому щоденний бекап — «звичайний»).
  Для стрибка вільне місце на його час рахуємо з повільним ростом без
  самих регулярних стрибків (інакше на «сходах» наступний бекап рахувався
  б двічі), а очікуване видалення попереднього бекапу додаємо, лише поки
  воно «очікується». Два числа: фізично бракує (до 100 %) і скільки
  звільнити, щоб після стрибка лишитися нижче 90 %.
- **Альтернативи:** години бекапу й видалення в налаштуваннях; окремі
  правила для кожного сервера; одразу складніші методи (AutoETS, LightGBM,
  Chronos-2, Prophet).
- **Чому:** прогноз має працювати на будь-якому диску (sim-1, sim-2, `my-pc`)
  без змін; лінійна регресія проста, швидка (мілісекунди) і пояснювана —
  «росте на 8,9 %/добу, до 90 % — 42 год». Складніші методи — пізніше,
  по одному, з порівнянням на стенді 2.2b.
- **Відомі особливості:** тренд описує повільну складову від останнього
  прибирання; під час швидкого заповнення він відстає (швидкий ріст ловить
  питання 2). Прогнози обмежено 0–100 %.

## Метод прогнозу для бота — лінійний (за стендом 2.2b, 2026-11-18)
- **Обрали:** попередження бота про заповнення диска — лінійний метод (три питання).
  Наївні методи в боті не використовуємо. Інтервал 10–90 % показуємо лише на +1 год.
- **Альтернативи:** наївний «як учора о цій порі» (точніший для рівня на +24 год на дисках
  зі щоденними бекапами); поєднання методів; складніші методи (AutoETS, LightGBM, Chronos-2).
- **Чому:** фінал — 200 прогонів seed 3 (налаштування — seed 1, версія 1 — seed 2; після
  seed 3 нічого не змінювали): пропусків немає; вчасно S4 19/19 (за 2,4 доби), S5 24/24
  (за 37 год), S6 24/24 (за 2,8 год), S7 24/24 (за 3,8 год); «не поміститься» для бекапу —
  14/14 заздалегідь; хибні тривоги 0 з 25 на S1–S3, 1–3 на S6–S8, 6–9 на S4/S5; похибка
  обіцяного часу до 90 % у першому попередженні — 2–9 год для S4/S6/S7 (для log_burst —
  оптимістичніше: медіана 2,6 доби проти 34 год); ~21 мс на диск. Наївні методи не
  попереджають взагалі (лише коли вже вище порогу). Слабкі місця — рівень на +24 год / +7 днів
  (щоденні бекапи, щотижневе прибирання), завузький інтервал на +24 год / +7 днів — у
  `docs/experiments/forecast_report.md`; доопрацювання — на потім.
- **Визначення стенду (після версії 1):** «дійшов до 90 %» — ≥ 5 хв поспіль і лише після
  початку перевірки; втручання — лише позапланові дії адміністратора (щотижневе прибирання
  передбачуване — не виключається ні з MAE, ні з хибних тривог).
- **Що змінено в прогнозі за результатами стенду (seed 1):** години до порогу — від меншого
  з прямої і факту (одразу після прибирання пряма ще на старому рівні); незвичний ріст — лише
  розподілений у часі (стрибок за одну хвилину — не ріст); пряма на +1 год — лише після
  сходинки; незвичний ріст не входить у тренд; вільне місце на час стрибка — без усіх
  завершених різких підйомів (вивантаження, що скінчилося, не «росте» далі). Після версії 1:
  пряма питання 2 — від «зламу», з якого почався ріст (лише коли за 30 хв ріст швидший за
  межу; щонайменше 15 точок); неповний останній 10-хв відрізок відкидаємо; завершений
  нерегулярний різкий підйом у тренді — як сходинка. Повний список з причинами — розділ
  «Що змінено під час налаштування» у звіті.

## Виняток із «симулятор заморожено»: сценарний стенд для прогнозу (2026-11-18)
- **Обрали:** `core/forecast_bench.py` генерує багато коротких незалежних
  прогонів тими самими класами симулятора (в пам'яті або тимчасовій базі;
  основна `oncall.db` не змінюється): ~10–14 днів норми, одна ситуація,
  кілька днів після; параметри випадкові в розумних межах. Ситуації
  S1–S8 по 20–30 прогонів. Пороги налаштовуємо на прогонах з одним seed,
  цифри для звіту — на прогонах з іншим. Плюс 30-денна історія як
  реалістичний змішаний приклад.
- **Альтернативи:** 90 днів в окрему базу `data/bench_forecast.db` з кожною
  ситуацією по 3–4 рази (перший варіант, відкинуто); лише 30-денна історія.
- **Чому:** у 30-денній історії кожна ситуація 1–2 рази й з одними
  параметрами — замало для висновків; 90-денний набір потрібен методам

  параметрами. Окремий seed для фінальних цифр — щоб не підганяти
  параметри під відповідь.

## Зміна плану: спершу дашборд і бот, покращення — через «іспит» (2026-11-20)
- **Обрали:** після кроку 2.2 — етап 0 (функції-інструменти `core/tools.py`
  + мінімальний дашборд) і етап 1 (бот + Claude через tool use, три режими
  для порівняння, іспит `tests/exam.yaml` і сторінка «Іспит»). Аналізатор,
  правила, алерти, живий потік і сценарії, Groq, порівняння методів —
  пізніше, окремо. Лінійний прогноз диска більше не змінюємо.
- **Одне джерело чисел:** функції `core/tools.py` — єдине місце, де
  рахуються факти; дашборд, бот, пізніше правила, аналізатор, REST API
  і текст алертів беруть числа лише з них; дашборд без власних SQL-запитів.
  Кожна функція бачить лише дані до моменту «зараз», не читає
  `sim_incidents`, повертає факти без висновків; час без поясу на вході —
  місцевий UTC+2, переводить код.
- **Альтернативи:** продовжувати за старим планом (2.3 правила → живий
  потік і сценарії → алерти → бот за шаблоном → LLM у фазі 3); RAG-підхід
  «зібрати всі факти в промпт» замість tool use.
- **Чому:**
  - до бота й дашборду якість модулів не видно на питаннях чергового,
    а покращувати модуль без виміру можна без кінця;
  - з однаковими функціями будь-яке число з відповіді бота можна знайти на
    дашборді в той самий момент — так легко перевірити, що LLM не вигадує;
  - «іспит» дає одне число якості, яким міряємо кожне наступне покращення
    (режими «без даних / сирі дані / інструменти» — як у практичній 3);
  - правильні відповіді іспиту рахує окремий простий запит, а не ті самі
    функції, — інакше помилка у функції «підтверджувала» б сама себе.

## Етап 0: функції-інструменти і дашборд (2026-11-20)

## Одне правило «дані застаріли» (2026-11-20)
- **Обрали:** кожен інструмент повертає `data_until`, `data_age_h` і `stale`
  (зараз − останні дані > 10 хв), а коли stale — ще `stale_note` словами.
  - `get_status`: останні відомі значення лишаються, з приміткою «останні відомі на …,
    N тому, а не поточні»; `age_h_now` бекапу — лише якщо перевірка не старша за 2 год.
  - Функції з вікном рахують лише за реальними даними у вікні: немає даних —
    «немає даних за період X–Y; останні — Z»; дані закінчились усередині вікна —
    пропуск у кінці (`gaps`) і примітка; ріст тек — за фактичні години (`measured_h`).
  - `get_disk_forecast`: коли stale, прогнозу «на зараз» немає (`disks` відсутнє);
    `forecast_at_last_data` — прогноз на момент останніх даних з позначкою «НЕ на зараз».
    Додано `to_threshold_pp` / `to_threshold_gb` — скільки лишилось до порогу.
  - «Наживо» (`now=None`) — справжній поточний час, а не останні дані.
  - Примітки: `notes` — ситуаційні (показує дашборд), `about` — постійні (лише для LLM).
- **Альтернативи:** лишити «наживо = останні дані» (тоді правило свіжості в історії
  і наживо різне); у stale-режимі рахувати все як є (давало ріст «0» і прогноз «на
  29.11» з даних 18.11); зовсім не давати прогнозу при stale (втрачається корисне
  «що було відомо востаннє»).
- **Чому:** коли момент пізніше за дані, функції поводились по-різному й частково
  вводили в оману (нулі, прогноз «наче зараз», поточні на вигляд картки). Бот на
  етапі 1 має чесно казати «свіжих даних немає», а не переказувати старі числа як
  поточні.
