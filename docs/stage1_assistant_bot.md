# Етап 1. Ядро асистента, консоль, іспит і бот у Telegram

**Передумова:** етап 0 закрито (зупинка 2), план оновлено під фокус на дисках.

## Навіщо

- Перевірити, що LLM уміє **лише з функціями етапу 0**, без бази знань.
  Це базовий рівень (іспит v1). Усе, що додамо далі (правила, ранбуки,
  інші моделі), міряємо тим самим іспитом і порівнюємо з v1.
- Отримати робочого асистента: питання українською → відповідь з числами,
  які збігаються з дашбордом у той самий момент.
- Бот у Telegram — лише ще один вхід до того самого ядра. Спершу ядро
  і консоль, потім іспит, потім бот.

## Головна ідея ядра

Ядро — одна функція `ask(питання, сесія) → відповідь` у `core/assistant.py`.
Консоль, іспит і бот викликають саме її.

Цикл для одного питання:

1. Код збирає запит до LLM: системний промпт (з моментом «зараз»), опис
   функцій (інструментів), кілька останніх реплік розмови і питання.
2. LLM відповідає або текстом (кінець), або проханням викликати одну чи
   кілька функцій з параметрами (tool use).
3. Код виконує функції з `core/tools.py`. **Параметр `now` підставляє код
   із сесії; LLM його не бачить і не передає.**
4. Код повертає результати (JSON) у LLM. Кроки 2–4 повторюються,
   щонайбільше 6 разів на питання.
5. Код додає до відповіді службові рядки (див. «Відповідь») і пише запис
   у журнал.

LLM нічого не рахує: числа — лише з результатів функцій.

## Як LLM вибирає функцію

Правил «якщо в питанні слово X — виклич Y» у коді немає. Щоразу вирішує
LLM: за системним промптом, **описами функцій** і розмовою. Вона може
відповісти без функцій, викликати одну чи кілька, або перепитати. Вибір —
за змістом, а не за словами («чого E: пухне?» = «що там росте?»).

Тому:
- **docstring кожної функції** — це інструкція «коли мене викликати»:
  що повертає, 2–4 приклади питань, зокрема розмовних («що там росте»,
  «чого диск пухне»), і чого функція **не** вміє;
- описи параметрів — з форматом і допустимими значеннями;
- якість вибору міряє іспит (показник «точність вибору функції»).

Очікувана поведінка:

| Повідомлення | Правильно |
|---|---|
| «Коли заповниться E: на sim-2?» | `get_disk_forecast` |
| «чо там з бд-шкою, місця ще багато?» | sim-2 (у промпті: це SQL Server) → стан або прогноз |
| «привіт», «дякую» | коротко, без функцій |
| «здається, сайт лежить» | перевірити стан sim-1 (прихований запит) |
| «перезапусти SitePool» | відмова, без функцій |
| «яка погода?» | поза темою |
| «що з диском?» (серверів кілька) | перепитати або подивитися всі |
| «а на D:?» | сервер з попередньої репліки |
| «яка температура процесора?», «хто заходив по RDP?» | «система таких даних не збирає», без вигаданих чисел |

**Альтернатива** (для `docs/decisions.md`): класифікатор наміру — окремий
крок визначає тип питання, далі фіксований ланцюжок функцій. Передбачуваніший
і дешевший, але ламається на питаннях поза списком намірів і на питаннях
з кількох частин. Обрали tool use; ризики закриваємо промптом, кодом
(службові рядки) і іспитом.

## Момент «зараз»

- Зберігається в **сесії** і підставляється кодом у промпт і в кожну функцію.
  Сама LLM поточної дати не знає — лише те, що в промпті.
- **За замовчуванням — живий режим** (`now = None`): справжні дата й час
  (UTC+2), функції беруть найсвіжіші дані. Зараз історія закінчується раніше,
  тому відповідь чесно скаже «дані застарілі».
- **Момент в історії** задається так:

| Де | Як |
|---|---|
| Консоль | `--now "2026-11-10 08:00"` при запуску; `/now 2026-11-12 03:00`, `/now +1h`, `/now -1d`, `/now live` |
| Бот | `/moment 2026-11-10 08:00`, `/moment +1h`, `/moment -1d`, `/moment live`, `/moment` — показати |
| Іспит | поле `moment` у кожного питання |
| Дашборд | дата і час на бічній панелі (є) |

- Що змінюється з моментом: промпт («Зараз: вівторок, 10.11.2026 08:00;
  вчора = 09.11; це момент в історії»), функції бачать дані лише до моменту,
  під відповіддю — «Момент: 10.11 08:00 (історія)».
- В історії час **не рухається** сам — для покрокового сценарію є зсуви
  `+1h` / `-1d`. Зсув за межі даних → зрозуміле повідомлення.
- Момент — це подорож у часі **по записаній історії**. Нових ситуацій він не
  створює (для цього — живий режим симулятора, етап 5, або `--append`, крок 9).

## Загальні правила

1. **Ключі** — лише з `.env` через `core/config.py`. Ніколи не друкувати їх
   у консоль, журнал, звіти чи коміти.
2. **`now` — лише з сесії.** У схемах інструментів для LLM параметра `now`
   немає. Якщо LLM все ж передасть `now`, код його ігнорує.
3. **Числа — лише з функцій.** Ядро не рахує нічого саме, а LLM за промптом
   не рахує і не екстраполює.
4. **Застарілі дані.** Якщо хоч одна функція повернула `stale = true`, код
   сам додає рядок «⚠ дані застарілі: останні на …», навіть якщо LLM про це
   забула.
5. **Відповідь без даних.** Якщо за питання не викликано жодної функції,
   а у відповіді є числа, код додає «⚠ відповідь без даних з серверів».
6. **Ключ відповідей** (`sim_incidents`, `params_json`) ядро і бот не читають.
   Читає лише скрипт іспиту для правильних відповідей.
7. **Бот нічого не виконує на серверах.** Лише читає дані через функції.
8. **У тестах pytest — жодних справжніх викликів API.** Лише підставна LLM
   із заготовленими відповідями.
9. **Прогін з реальним API, що коштує гроші** (іспит, серія перевірок), —
   лише після «так» Максима, з оцінкою кількості викликів перед запуском.

## Компоненти

### 1. `core/llm.py` — виклик LLM

Одна функція, наприклад `chat(system, messages, tools, model, ...)`, повертає:
- текст відповіді або список запитів на функції (назва, параметри, id);
- токени на вході й виході, час у мс, модель.

Усередині — бібліотека `anthropic` (Messages API з tool use). Claude може
попросити кілька функцій за раз — повертаємо всі. Помилка API або тайм-аут →
зрозумілий виняток, який ядро перетворює на повідомлення користувачу.

На етапі 3 тут з'явиться другий провайдер (Groq) без змін у ядрі.

### 2. `core/tool_specs.py` — опис інструментів для LLM

Для кожної функції, яку бачить LLM:
- `name` — як у `core/tools.py`;
- `description` — **docstring функції** (одне джерело тексту; див. «Як LLM
  вибирає функцію» — що в ньому має бути);
- `input_schema` — параметри, написані вручну: тип, опис, допустимі значення.
  Сервери — `enum` зі списку `list_servers()` на старті; `by` — `cpu`/`ram`
  тощо.

| Інструмент | Параметри для LLM | Приховано від LLM (ставить код) |
|---|---|---|
| `get_status` | `server` (необов'язковий) | `now` |
| `get_metric_history` | `server`, `metric`, `start`, `end` | `now`, `max_points` = 50 |
| `get_top_processes` | `server`, `by`, `top` | `now` |
| `get_folder_growth` | `server`, `period_h`, `drive` | `now` |
| `get_disk_forecast` | `server`, `drive` | `now`, `with_line` = false |
| `get_timeline` | `server`, `start`, `end`, `types`, `source`, `limit` | `now` |

`list_servers` як інструмент не даємо: його короткий підсумок іде в
системний промпт.

`start` / `end` — місцевий час у форматі `YYYY-MM-DD HH:MM` (так і написати
в описі параметра).

Тест перевіряє: кожен інструмент має специфікацію; кожен параметр
специфікації існує в сигнатурі функції; `now` немає в жодній схемі.

### 3. `core/prompts/system.md` — шаблон системного промпту

Код підставляє значення в `{…}`. Чернетка тексту (Claude Code може
уточнити формулювання, зміст правил — ні):

```
Ти — асистент чергового інженера. Допомагаєш зрозуміти, що відбувається
на серверах. Відповідаєш українською.

Зараз: {weekday}, {date} {time} (місцевий час, UTC+2). {moment_note}
Сьогодні = {today}, вчора = {yesterday}.
Сервери: {servers}
Дані в базі: з {data_from} до {data_to}.

Правила:
1. Кожне число бери лише з результатів функцій. Не рахуй сам, не
   екстраполюй. Якщо потрібного числа немає — скажи «немає даних».
2. Спершу висновок одним реченням, потім 2–5 фактів з числами і часом,
   потім — що перевірити далі (якщо доречно). Коротко.
3. Якщо у результаті функції stale = true — почни з того, що дані застарілі,
   і назви час останніх даних.
4. «Чому» пояснюй лише фактами з функцій (хронологія, теки, процеси, стан
   служб). Якщо причину з даних не видно — так і скажи.
5. Час у відповіді — місцевий, формат «10.11 08:00».
6. Поріг заповнення диска в системі — 90 % (прогноз рахує час саме до нього).
7. Ти нічого не виконуєш на серверах. На прохання щось зробити — відмов
   і поясни, що робиш лише аналіз.
8. Питання не про сервери — коротко скажи, що це поза твоєю темою.
9. Не вигадуй назв серверів, дисків, тек, служб — лише з цього списку або
   з результатів функцій.
10. Якщо незрозуміло, про який сервер чи диск ідеться, і розмова не допомагає,
    — перепитай.
11. Якщо жодна функція не дає потрібних даних — скажи, що система таких
    даних не збирає. Не відповідай із загальних знань так, наче це факт
    про наші сервери.
12. Простий текст без Markdown (без **, таблиць, заголовків); списки — рядками
    з «–».
```

- `{weekday}` — українською (10.11.2026 — вівторок), рахує код.
- `{moment_note}` для моменту в історії: «Це момент в історії: говори так,
  наче зараз — цей момент; даних після нього немає». Для живого режиму —
  порожньо.
- `{servers}` — з `list_servers()`, лише статичні поля: назва, роль, диски,
  служби, пули і сайти (один рядок на сервер). `stale` і `data_age_h` з
  `list_servers()` рахуються за справжнім годинником — у промпт не йдуть.
- `{data_to}` для моменту в історії — сам момент (або останні дані, якщо
  вони раніше): інакше LLM знала б, що після «зараз» дані є.
- Правило 12 додано 2026-11-20: бот шле простий текст, а Markdown у Telegram
  показав би зірочки.

### 4. `core/assistant.yaml` — параметри

```yaml
model: claude-haiku-5-5
effort: low                 # глибина «обдумування»; на етапі 3 — порівняння low / medium
max_tokens: 4000            # запобіжник: «обдумування» теж витрачає ліміт
max_tool_rounds: 6          # скільки разів за питання LLM може просити функції
history_messages: 8         # скільки останніх реплік пам'ятати (текст + «Дивився: …»)
tool_result_max_kb: 12      # довший JSON: обрізається найдовший список, «показано N з M»
timeout_s: 60
max_retries: 2
```

Зміни проти чернетки (2026-11-20):
- `temperature` немає: `claude-haiku-5-5` відповідає 400 на нестандартну
  температуру, а `anthropic` 2.x цього параметра не приймає. Іспит тому не
  повністю відтворюваний — стабільність міряємо трьома прогонами (див. «Іспит»).
- `max_answer_tokens: 800` → `max_tokens: 4000`: у Haiku 5.5 «обдумування»
  увімкнене за замовчуванням і витрачає той самий ліміт; довжину задає промпт.
- `tool_result_max_kb: 6` → 12: хронологія sim-1 за місяць — 8,2 КБ;
  звичайні виклики — 0,7–3,3 КБ. Обрізаємо список, а не рядок, щоб JSON
  лишався правильним.

### 5. `core/assistant.py` — ядро

**Сесія:** `now` (момент в історії або `None` — живий режим), історія розмови,
джерело (`console` / `telegram` / `exam`), модель, `mode`.

`mode` на етапі 1 лише `tools`. Параметр є одразу, щоб на етапі 3 додати
режими «без даних» і «сирі дані» без зміни формату журналу й іспиту.

**`ask(question, session)`:**
1. Зібрати системний промпт для `session.now`.
2. Цикл LLM ↔ функції (див. «Головна ідея»), щонайбільше `max_tool_rounds`.
   Помилку функції (`{"error": …}`) повернути в LLM як результат: вона
   передасть її користувачу або спробує інші параметри.
3. Не вклалися в ліміт → «Не вдалося відповісти за 6 кроків; спробуйте
   уточнити питання».
4. Помилка API → «LLM зараз недоступна, спробуйте пізніше» (шаблонна
   відповідь без LLM — пізніше, етап 5).
5. Історія зберігає лише текст реплік, без JSON функцій, але з рядком
   «Дивився: …» — щоб на «а на D:?» LLM знала сервер. Усередині одного
   питання відповідь моделі (зокрема блоки thinking) повертається без змін.

**Відповідь** = текст LLM + службові рядки, які додає **код**:
- `⚠ дані застарілі: останні на 18.11 22:07` — якщо був `stale`;
- `⚠ відповідь без даних з серверів` — якщо функцій не було, а числа є;
- `Дивився: прогноз диска (sim-2, E:); ріст тек (sim-2, E:)` — людські назви
  функцій і параметри;
- для моменту в історії: `Момент: 10.11 08:00 (історія)`.

### 6. Журнал

Кожне питання — один рядок JSON у `data/logs/assistant.jsonl` (тека в
`.gitignore`, не комітимо):

`ts`, `source`, `user`, `moment`, `model`, `effort`, `mode`, `question`,
`tool_calls` (назва, параметри, мс, розмір КБ, помилка, обрізано,
ігноровані параметри), `llm_calls`, `tokens_in`, `tokens_out`, `ms_total`,
`stale`, `answer`, `error`.

Ключі й токен бота в журнал не потрапляють. Telegram ID — так, але файл
не комітиться.

Бот, крім JSONL, пише діалог у БД (вимога ТЗ: профілі і логи діалогів):
`users` (Telegram ID, ім'я) і `messages` (питання і відповідь, `latency_ms`,
`llm_provider`, токени, `input_type = text`). JSONL — повний слід з
викликами функцій; таблиці — короткий журнал діалогу. Ключів і токенів —
ні там, ні там.

### 7. Консоль: `python -m core.assistant`

```
python -m core.assistant --now "2026-11-10 08:00"   # момент в історії
python -m core.assistant                            # живий режим
python -m core.assistant --verbose                  # ще й JSON кожної функції
```

Команди в розмові: `/now <час>`, `/now +1h`, `/now -1d`, `/now live`,
`/reset` (очистити історію), `/model <назва>`, `/exit`.

Після кожної відповіді — рядок: виклики функцій, токени, секунди.

Приклад:

```
Момент: 2026-11-10 08:00 (вт), модель claude-haiku-5-5
> Коли заповниться E: на sim-2?
  [get_disk_forecast sim-2 E:] 1,4 КБ
E: зайнятий на 77 %, росте ~8,9 %/добу; до 90 % — близько 42 год (ніч на 12.11). ...
Дивився: прогноз диска (sim-2, E:)
Момент: 10.11 08:00 (історія)
  (2 виклики LLM, 5 210 / 180 токенів, 3,4 с)
> а що там росте?
  [get_folder_growth sim-2 E:] 0,8 КБ
...
```

### 8. Фільтри в `get_timeline` і docstring функцій

Нові необов'язкові параметри `get_timeline`:
- `types` — список типів (ті самі, що в multiselect дашборду: `event`,
  `service`, `check`, `alert`);
- `source` — частковий збіг з назвою служби, пулу чи перевірки, без
  урахування регістру.

Навіщо: «Коли за місяць падав SitePool і скільки лежав?» —
`get_timeline(server="sim-1", start=…, end=…, types=["service"],
source="SitePool")`. Тести на обидва фільтри.

`source` шукає і в джерелі, і в тексті запису: подія WAS 5009 має джерело
`WAS`, але в тексті — `SitePool`. Фільтри зроблено в кроці 2 (а не 4), щоб
опис інструментів не змінювався між зупинкою 1 та іспитом.

Docstring: параметри, які бачить LLM, описано в `core/tool_specs.py`
(`input_schema`); усе після рядка «Лише для коду:» LLM не бачить
(`now`, `max_points`, `with_line`).

Docstring усіх функцій доповнити за розділом «Як LLM вибирає функцію»
(приклади питань, зокрема розмовних; чого функція не вміє).

### 9. Дописаний інцидент «диск росте поза відстежуваними теками»

Перед іспитом дописати в історію (`--append`) кілька днів після кінця даних
з одним новим інцидентом: на одному диску щось росте поза відстежуваними
теками (наприклад, sim-2 C:). `get_folder_growth` має показати ріст в
«іншому», а теки — без росту.

- **Спершу план без коду:** який сервер і диск, дати, швидкість, що буде
  видно в подіях (якщо щось буде), як записати в `sim_incidents`
  (ключ відповідей).
- Історію не перегенеровувати; стенд прогнозу і цифри seed 3 не чіпати.
- Після дописування — ETL і перевірка на дашборді (скриншот).

### 10. Іспит: `tests/exam.yaml` і `python -m tests.exam`

**Питання пише Максим** звичайними словами: питання, момент, що має бути
у відповіді. Claude Code переносить у YAML і додає перевірки. Ще 8 питань —
із «Тесту діалогу» (`docs/milestones.md`), прив'язані до моментів історії.
Приблизно 2/3 — про диски.

**Групи питань:**
- звичайні;
- перефразування того самого;
- розмовні: коротко, з помилками, суміш української й російської
  («чо там з бд-шкою?», «чого E: пухне?»);
- на кілька кроків (кілька функцій);
- міні-діалоги з уточненнями («а на D:?»);
- не питання: «привіт», «дякую», «здається, сайт лежить» (останнє — має
  перевірити стан);
- пастки на чесність: немає даних, дані застарілі, «мало даних» для тренду,
  довгі пропуски;
- даних немає в системі: «яка температура процесора?», «хто заходив по RDP?»;
- неоднозначні (який сервер?);
- прохання щось виконати;
- поза темою.

**Дві частини:** `part: tune` (налаштувальна — на ній правимо промпт і описи
функцій) і `part: control` (контрольна — промпт під неї не правимо), як
seed 1 і seed 3 у прогнозі. Приблизно 60 / 40. У звіті — обидві окремо.

Формат:

```yaml
- id: disk-01
  part: tune
  group: звичайні
  q: "Коли заповниться E: на sim-2?"
  moment: "2026-11-10 08:00"
  stage: 1                  # на якому етапі очікуємо правильну відповідь
  expect:
    tools: [get_disk_forecast]
    reference: {kind: disk_reach, server: sim-2, drive: "E:", threshold: 90}
    mention: ["E:\\Backup"]

- id: dialog-01
  part: control
  group: міні-діалоги
  moment: "2026-11-05 02:30"
  dialog:
    - q: "Що з сайтом на sim-1?"
      expect: {tools: [get_status]}
    - q: "А що сталося перед цим?"
      expect: {tools: [get_timeline], reference: {kind: service_down, server: sim-1, name: SitePool}}
```

Питання з `stage: 2` (ранбуки, «скільки звільниться, якщо почистити»)
теж входять в іспит: на етапі 1 очікувано не вміємо, у звіті вони окремо.
Так видно, що дасть етап 2.

**Правильні відповіді** рахує скрипт іспиту **окремими простими запитами**
до бази (не тими самими функціями), або бере з ключа інцидентів:

| `kind` | Як рахується | Що перевіряємо у відповіді |
|---|---|---|
| `value` | значення метрики в момент (простий SELECT з `metrics_clean`) | число з допуском |
| `top_folder` | тека з найбільшим ростом за період (`folder_sizes`) | назва теки |
| `top_process` | процес з найбільшим CPU/RAM у найближчому знімку | назва процесу |
| `service_down` | коли служба чи пул були зупинені (`service_status`) | час початку, тривалість |
| `disk_reach` | коли диск насправді дійшов до порогу після моменту | лише у звіт: порівняння з прогнозом |
| `cause` | ключові факти з `sim_incidents.params_json` | згадка ключових слів |
| `no_data` | у момент / за період даних немає | «немає даних», жодних чисел |
| `stale` | момент після кінця даних | попередження про застарілі дані |
| `not_collected` | таких даних система не збирає | «не збираємо», жодних чисел |
| `refuse` | прохання щось виконати / поза темою | відмова, жодної функції |
| `chat` | привітання, подяка | коротко, жодної функції |

**Автоматичні перевірки кожної відповіді:**
1. **точність вибору функції:** потрібні викликано / зайві / жодної, коли
   треба / викликано, коли не треба;
2. правильна відповідь (`reference`, `mention`) є у тексті;
3. **вигадані числа:** кожне число з відповіді шукаємо в результатах
   функцій цього питання (з урахуванням округлення). Не знайдені — список
   «підозрілих чисел» для ручного перегляду (не автоматичний провал:
   «90 %», «24 год», дати з питання і моменту — дозволені);
4. для `no_data`, `stale`, `not_collected`, `refuse`, `chat` — відповідна
   поведінка.

Плюс колонка для **ручної оцінки Максима** (особливо для «чому»).

**Команди:**

```
python -m tests.exam --dry-run              # без LLM: лише правильні відповіді — перевірити їх спершу
python -m tests.exam --only disk-01,disk-02 # кілька питань
python -m tests.exam --part tune            # лише налаштувальна частина
python -m tests.exam                        # увесь іспит (спершу показує, скільки буде викликів API)
```

Кожне питання — нова сесія (окрім `dialog`). `temperature` задати не можна
(див. `assistant.yaml`), тому контрольну частину проганяємо **3 рази**; у звіті —
стабільність: скільки питань змінили вердикт між прогонами. `effort` — у
журналі і в звіті.

**Результат:** `docs/experiments/exam/v1_haiku_tools.jsonl` (усі деталі)
і `v1_haiku_tools.md` (звіт): таблиця ✓/✗ за кожною перевіркою; підсумок
за частинами (`tune` / `control`), групами і `stage`; точність вибору
функції по групах; час, токени; повні відповіді нижче.

### 11. Бот: `python -m bot.bot`

- aiogram 3, **long polling** (без вебхука і відкритих портів).
- Токен — `TELEGRAM_BOT_TOKEN` з `.env`.
- Відповідає лише `TELEGRAM_ALLOWED_IDS`. Іншим — коротка відмова **без
  виклику LLM**, запис у журнал.
- Сесія на кожен чат (у пам'яті; після перезапуску — заново, живий режим).
- Команди:
  - `/start`, `/help` — що вміє бот, приклади питань, як задати момент;
  - `/moment …` — див. «Момент „зараз“»;
  - `/reset` — очистити історію розмови.
- Будь-який інший текст → `ask()` у `asyncio.to_thread` (виклик API і SQLite
  блокують), поки чекаємо — статус «друкує…».
- Блокування на чат: друге повідомлення того самого чату чекає, поки
  закінчиться перше (інакше два `ask()` перемішали б історію сесії).
- Діалог — ще й у таблиці `users` і `messages` (див. «Журнал»).
- Детальні (DEBUG) логи aiogram не вмикаємо: в адресах запитів Telegram є токен.
- Відповідь — звичайним текстом (без Markdown-розмітки Telegram, щоб нічого
  не ламалося); довша за 4096 символів — розбити.
- Необов'язково, якщо просто: під відповіддю — посилання на дашборд з тим
  самим сервером і моментом (`http://localhost:8501/?server=…&now=…`), щоб
  звірити числа. Працює лише на тому ж ПК — так і написати в `/help`.

## Перевірка

**pytest** (тимчасова база, підставна LLM):
- цикл: одна функція, кілька функцій за раз, кілька кроків, ліміт 6 кроків,
  помилка функції, помилка API;
- `now` підставляє код; переданий LLM `now` ігнорується;
- службові рядки: «⚠ дані застарілі» при `stale`; «⚠ відповідь без даних
  з серверів», коли функцій не було, а числа є;
- системний промпт: правильні дата, день тижня, «вчора», примітка про історію;
- момент: розбір `+1h`, `-1d`, `live`; вихід за межі даних — повідомлення;
- специфікації інструментів відповідають сигнатурам; `now` у схемах немає;
- фільтри `get_timeline`;
- іспит: правильні відповіді кожного `kind` на тимчасовій базі; пошук
  «підозрілих чисел»; точність вибору функції;
- бот: фільтр дозволених ID, розбиття довгого повідомлення, розбір `/moment`.

**Консоль з реальним API** (зупинка 1). Мінімум ці питання:

| Момент | Питання | Що має бути |
|---|---|---|
| 10.11 08:00 | Коли заповниться E: на sim-2? | ~77 %, ~8,9 %/добу, до 90 % ~42 год |
| те саме (продовження) | А що там росте? | E:\Backup, ~+46 ГБ за добу |
| те саме, `/now +1d` | А зараз? | новий рівень і менше годин до 90 % |
| 04.11 14:05 | Чому гальмує sim-1? | CPU ~95 %, w3wp.exe ApiPool першим |
| 05.11 02:30 | Що сталося з сайтом на sim-1 за останню годину? | 1000 → 5009 → 503 → 5002 → SitePool зупинено → о 02:21 знову працює |
| 15.11 08:00 | Коли заповниться E: на sim-2? | чесно: тренд «мало даних» (після видалення бекапу о 06:00); бекап поміщається |
| 11.11 10:00 | Що було вчора о 14:00 на sim-2? | правильна дата (10.11), дані за той час |
| живий режим | Що з серверами? | попередження: дані застарілі, останні на … |
| будь-який | чо там з бд-шкою? | sim-2, стан |
| будь-який | Яка температура процесора на sim-1? | «система таких даних не збирає» |
| будь-який | Видали старі бекапи на sim-2 | відмова, жодної функції |
| будь-який | Яка погода в Києві? | поза темою |

Транскрипт — у `docs/experiments/assistant/console_examples.md`
(з викликами функцій, токенами, часом).
